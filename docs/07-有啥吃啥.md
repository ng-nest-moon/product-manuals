# 有啥吃啥 — 产品功能说明书

## 一句话定义

对着冰箱拍一张，AI 给你配好一桌菜，附带做法，做了就完事。

---

## 一、目标用户与痛点分析

### 1.1 核心用户画像

**主要用户：做饭但不想想做什么的人（28-45 岁）**

| 维度 | 描述 |
|------|------|
| 年龄 | 28-45 岁 |
| 状态 | 需要每天做饭（独居/有家庭） |
| 做饭频率 | 每周 4-7 次 |
| 典型状态 | 打开冰箱不知道做什么，最后做了一样的 |
| 底层心理 | "要是有人替我想好了就好了" |

### 1.2 真实痛点分级

| 需求类型 | 痛点 | 用户行为证据 |
|---------|------|-------------|
| **刚需** | 每天想"吃什么"消耗大量心力 | "吃什么"是家庭高频困扰问题 |
| **刚需** | 打开冰箱有食材但搭配不起来 | 食材买了但不知道能做成什么 |
| **改善型** | 做的菜总是那几样，想换但懒得想 | 缺乏灵感，不是缺乏技能 |
| **改善型** | 做完菜还要记"这个菜怎么做" | 需要快速获取做法指引 |
| **猎奇伪需求** | "我要做个大餐" | 日常做饭不需要米其林，用户只想快速解决 |

---

## 二、解决方案与核心功能

### 2.1 解决方案概述

有啥吃啥是"最不需要动脑子的做饭工具"。拍冰箱 → 出菜单 → 做完收工。没有收藏、没有评分、没有社区、没有一周规划。

不让你选的逻辑：
- **不出多套方案** — 出一整桌，不让用户凑
- **不做推荐列表** — 直接给结果
- **不保留历史** — 做了就过了
- **不记录健康数据** — 只做家常菜

### 2.2 核心功能清单

1. **拍照识别** — 对冰箱/台面/橱柜拍照，AI 识别现有食材
2. **智能配菜** — 按人数、时间、天气、偏好出一桌菜
3. **做法输出** — 每道菜附带 3~5 句简明做法
4. **反馈学习** — 用户做完了点"搞定"，系统自动优化推荐

## 三、竞品与差异化分析

| 竞品 | 优点 | 缺点 | 差异 |
|------|------|------|------|
| 下厨房 App | 菜谱丰富，用户社区大 | 需要主动搜索选择，有"太多选择"的问题 | 有啥吃啥不让你选，直接出结果 |
| 小红书食谱 | 漂亮、有趣 | 搜索成本高，适合种草不适合日常 | 有啥吃啥从冰箱出发，不是你想到出发 |
| 盒马/叮咚 | 可以直接买菜 | 解决的是"买什么"不是"做什么" | 有啥吃啥解决的是"现有食材怎么做" |

**差异化优势：** 从"你有的"出发直接配菜，省掉"想吃什么"这个环节。

## 四、架构总览

```
用户拍照/语音输入
    ↓
视觉识别 / 语音识别 (GPT-4o / Gemini)
    ↓
推荐引擎
  规则 + 用户历史偏好
  (不重复 / 快过期优先 / 天气 / 人数)
    ↓
菜谱输出
  一桌菜 · 做法 · 用时
```

## 五、核心模块详解

### 5.1 输入方式

| 方式 | 说明 |
|------|------|
| 拍照 | 拍冰箱/台面/橱柜，一次最多 3 张 |
| 语音 | 说「有鸡蛋番茄青椒」也行 |
| 手动补 | 识别错了？拍完直接打字补一两个词「还有葱」 |

### 5.2 推荐逻辑（按优先级）

1. **昨天做了啥** → 今天不重复
2. **冰箱里最快要过期的** → 优先用掉
3. **上次做完你点了👍的** → 相近的优先
4. **今天天气** → 热天偏凉拌/冷天偏炖汤
5. **今晚时间** — 如果日历显示有会到 8 点 → 做 20 分钟内搞定的
6. **家里有小孩** → 排除辣菜、刺多的鱼、整颗坚果，优先好入口的
7. **以上都没命中** → 随机出一道能做的

### 5.3 输出规则

按人数出一桌菜：

| 人数 | 道数 | 搭配 |
|------|------|------|
| 1 人 | 1 道 | 盖饭/炒面类一锅出 |
| 2 人 | 2 道 | 1 荤 1 素 |
| 3~4 人 | 3 道 | 1 荤 1 素 1 汤 或 2 荤 1 素 |
| 5+ 人 | 4 道 | 2 荤 1 素 1 汤 |

每道菜附带：菜名、预计用时、做法（3~5 句话，不超过 60 字）、还缺啥（可选）

### 5.4 硬约束

- **只出家常菜** — 排除烘焙、西餐、复杂料理
- **每道不超 30 分钟** — 从开火到上桌
- **调料不超过 6 样** — 油盐酱醋糖料酒这类常备的不算
- **全部菜合计不超 45 分钟**
- **可以用剩菜/隔夜饭改造**

### 5.5 反馈循环

| 用户动作 | 系统学到 |
|----------|----------|
| 点「搞定」 | +1，以后类似优先 |
| 没点搞定，关掉 App | -1，以后少推 |
| 手动说「今晚做的水煮鱼」并拍照 | 更新偏好 |
| 连续 3 次没反馈 | 降低频次，问是否不准 |

## 六、用户流程

```
首次：设定吃饭人口（大人/小孩数量）
    ↓
每日：打开 App → 拍冰箱/厨房 → 等 3 秒
    ↓
看到一桌菜（荤素搭配好了，每道菜有做法）
    ↓
做完 → 点「搞定」
```

没有「选一个」的步骤。没有第二屏。没有收藏、没有评分、没有社区。

## 七、商业模式

| 付费模式 | 定价 | 依据 |
|---------|------|------|
| 免费基础版 | 0 元 | 每日 3 次配菜，入门体验 |
| 订阅 Pro | 10-15 元/月 | 不限次数，人数/天气/偏好全部功能 |

**销售渠道：** App Store / 安卓应用商店。初期不做独立推广，靠搜索"做饭"相关关键词自然获取。

**盈利模式：** 纯订阅，无广告。免费版足够日常使用，Pro 针对高频用户。

## 八、落地路径

### 8.1 落地难点

| 难点 | 缓解策略 |
|------|---------|
| 食材识别不准 | 首次先上语音/手动补充兜底，视觉持续迭代 |
| 推荐结果用户不喜欢 | 反馈循环逐步学习偏好 |
| "每天做一样的"用户不满意 | 不重复规则确保差异化 |
| 用户没有拍照习惯 | 反馈机制让用户看到"拍一下就能解决" |

### 8.2 MVP

- 拍照识别（常见蔬菜水果 + 基础冷冻食品）
- 1-2 人配菜逻辑
- 3 类输出（饭/面/炒菜）
- 纯 HTML 原型或小程序

### 8.3 第一步验证

**最关键假设：** 用户愿意在做每顿饭前拍一张冰箱。

**验证方法：** 做个 Telegram bot — 用户发照片收到菜谱。关键指标：用户是否会在第二天继续拍。如果 7 天内再次使用率 > 40%，需求成立。

## 九、风险与预期反馈

| 预期槽点 | 应对方案 |
|---------|---------|
| "识别错了" | 手动补词入口，不影响主流程 |
| "出的菜我不喜欢" | 反馈学习，但不提供"多选"方案 |
| "太简单了" | 就是要简单——复杂我们不做 |
| "没有我想吃的" | 那你自己想——我们就是帮你不用想的 |

## 十、边界声明

| 不做 | 理由 |
|------|------|
| 社区/分享 | 跟省脑子矛盾 |
| 自建菜谱库 | 对接现有 API 即可 |
| 一周规划 | 跟每天拍每天做矛盾 |
| 营养计算 | 用户没要 |
| 购物车/买菜 | 可后加，初版不做 |
| 多选凑菜 | 出一整桌，不让用户凑 |
